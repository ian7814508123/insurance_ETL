## 類型說明

### 1. 通用型（General / Base）定義：
* 不論買哪一種人身保險，只要是「保險契約」就一定會存在的底層架構、法律關係人、或共通權利義務。
* 核心特徵：名詞多出自《保險法》總則或一般商業保險契約條款（如：要保人、催告、契約暫停與恢復）。
### 🏥 2. 健康保險型（Health）定義：
* 以被保險人「疾病」或「身體傷害」為保險事故，補償因醫療行為產生的費用或經濟損失。
* 核心特徵：圍繞在醫療機構、診療行為、疾病診斷。
* 名詞常涉及健保、手術、住院。
* 細分亞型之定義：
  * 一般醫療險：保障因住院、手術產生的實支實付（收據）或日額補償。
  * 癌症險：專門針對罹患「惡性腫瘤」後的治療給付。
  * 重大傷病/疾病險：經診斷符合特定重大疾病（如心肌梗塞）或取得健保重大傷病證明。
  * 長照/失能險：因生理或認知障礙（如巴金森氏症、失智），導致長期需要他人照顧。
### ⚡ 3. 傷害（意外）保險型（Injury / Accident）定義：
* 以被保險人遭受「外來、突發、非疾病」的意外傷害事故，致身體蒙受傷害、失能或死亡為保險事故。
* 核心特徵：強調事故發生的外部性。若致殘，會嚴格對照官方的「失能程度與保險金給付表」（1~11級、80項失能）。保費與年齡無關，與職業危險等級有關。
###  📈 4. 投資型保險型（Investment-Linked）定義：
* 保險公司將保戶繳交的保費，一部分用於保險保障，另一部分放置於專設帳戶（分離帳戶）進行投資。保戶需「自行承擔投資風險」。
* 核心特徵：充滿金融市場、證券投資、帳戶管理的名詞。資產價值會隨市場波動。
### 💰 5. 壽險與年金保險型（Life / Annuity / 儲蓄型）定義：
* 人壽保險：以人的「生命（身故或生存）」為保險事故。
* 年金保險：在被保險人生存期間，保險人按照約定期間（如按月、按年）給付年金，用以對抗「活太久」的長壽風險。
* 核心特徵：圍繞在時間、利率、資金退還。名詞多涉及保單價值準備金、預定/宣告利率、生存/滿期給付。
```logic
IF 名詞涉及「專設帳戶/配置/市場評價」 ➜ 歸類至投資型
ELSE IF 名詞涉及「疾病/健保/手術/住院/照護」 ➜ 歸類至健康型
ELSE IF 名詞涉及「非疾病/突發外來事故/職業等級」 ➜ 歸類至傷害型
ELSE IF 名詞涉及「生存金/滿期/年金給付/利率變動」 ➜ 歸類至壽險與年金型
ELSE（所有保單皆會出現的權利義務/法律關係人） ➜ 歸類至通用型
```

#### 補充: 錯誤歸納造成的影響可能
* 目前我認為錯誤歸納子類詞庫造成的影響是降低未來在解析商品時要檢索名詞定義的效率。
例如. 某商品屬於傷害險, 腳本或agent會優先去 通用+傷害 兩種子詞庫進行檢索, 但其中一個名詞定義被誤歸類在醫療,導致多了更多次的查找。
但最後的決策樹只有兩種結果: 1. 在某個子類找到該定義 2. 都沒有找到, 視為新名詞

* 另外一種潛在的風險: 產品所屬範疇過廣,分類依據可能會失效
例如. 某個商品同時有意外傷害、醫療的特質,此時需要判定其所屬的險種就會比較困難(沒有明確邊界),此時他的判斷依據也會很難以追蹤

### 🧪 複本管理與 A/B 測試架構建議

針對您提出的 Method 1 與 Method 2 之 A/B 測試與詞庫載入機制的腳本管理，我強烈建議遵循以下**「軟體工程最佳實踐」**，以避免專案陷入維護地獄：

#### 1. 🗄️ 資料與詞庫層面：反對手動維護多份實體複本！
*   **單一事實來源 (Single Source of Truth, SSOT)**：
    *   我們應以 **Method 1 的 5 類子詞庫** 作為專案中的「黃金標準 (Gold Source)」。
    *   **拒絕在 Git 中手動管理 Method 2 的數百個單檔**。否則，未來手動同步子詞庫 JSON 與對應的單檔 JSON 會極易出錯。
*   **動態降維編譯 (On-the-fly Compilation)**：
    *   在測試 Method 2 時，應撰寫一個簡單的自動化編譯腳本（例如 `compile_to_single_files.py`）。
    *   每次測試前，該腳本會自動讀取 5 類子詞庫，動態在臨時目錄中（例如 `data/definitions/temp_single_files/`）解構成單檔。這樣兩套方法在資料上永遠保持 100% 同步，完全不需要手動做複本管理。

#### 2. 💻 腳本與程式碼層面：使用「策略模式」，拒絕複製腳本
*   **拒絕複製檔案**：千萬不要將 `orchestrator.py` 複製一份成 `orchestrator_method2.py`。這會導致日後 Pipeline (如 Registry 或 Param Builder) 的其他重大改進無法自動同步。
*   **策略模式 (Strategy Pattern) 實作**：
    *   在 `src/pipeline/orchestrator.py` 中，我們可以使用「策略模式」來處理載入與比對。
    *   透過一個簡單的組態變數 `config.LOADER_STRATEGY` 或 CLI 參數 `--strategy` 來切換載入邏輯：
    ```python
    # 策略模式偽代碼示意
    if config.LOADER_STRATEGY == "CLASSIFIED":
        # 執行 Method 1 的分類子詞庫載入邏輯
        primary_defs = load_classified_defs(detected_category)
    elif config.LOADER_STRATEGY == "SINGLE_FILE":
        # 執行 Method 2 的動態單檔載入與對齊邏輯
        primary_defs = load_dynamic_single_defs(document_contents)
    ```

#### 📊 A/B 測試的核心觀測指標
當您切換這兩個策略進行測試時，應著重比對以下指標：
1.  **對齊精準度 (Alignment Accuracy)**：分析產出的 `NEW_GENERAL` 數量，驗證是否有已存在的定義未被正確對齊（Method 2 的動態檢索容易因為條文些微錯字或用詞差異而漏載入單檔，造成召回率下降）。
