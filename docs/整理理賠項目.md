# 任務規劃：整理理賠項目 (Claim Items) 子詞庫化

本文件旨在規劃將名詞定義已驗證成功之 **Method 1 (CLASSIFIED - 險種分類)** 機制推廣至理賠項目（`claim_item`）的任務內容與開發時程估計。

---

## 1. 任務背景與目的

在先前的 PoC 測試中，我們依據 [整理名詞定義-full.md](file:///c:/Users/User/Downloads/保費試算/docs/整理名詞定義-full.md) 證實了：
* **Method 1 (CLASSIFIED - 險種分類)** 載入機制在名詞定義檢索上效率最高（平均單檔處理時間縮短至 33 秒，效能極其穩定且波動極小）。
* 它能有效降低傳入 LLM 的 Context Token 數量，降低 API 成本，同時維持高精準度的對齊效果。

為了延續此一技術優勢並保持系統架構的一致性，我們決定將此方法套用到理賠項目中：
* 將原本單一且龐大的 `base_claim_items.json` 拆分成 5 類子理賠項目庫。
* 升級管理端（`manager.py`），提供人機互動審查機制與跨詞庫防禦性去重。
* 升級 Pipeline 端（`orchestrator.py`），實作險種動態載入與備用庫 fallback 雙層對齊。

---

## 2. 理賠項目分類依據

理賠項目將與名詞定義保持相同的 5 大險種分類邊界，並使用既有的關鍵字規則引擎與 LLM 進行語義判定：

| 險種分類 | 英文代號 | 核心判定特徵 / 白話邏輯 |
| :--- | :--- | :--- |
| **通用型** | `general` | 不論險種，所有保單皆可能出現的通用或法律給付（如：身故保險金、完全失能保險金、解約金、保險費退還）。 |
| **健康保險型** | `health` | 圍繞疾病、醫療行為、住院、手術、健保、癌症、特定傷病、長期照顧、生理/認知功能障礙等理賠給付。 |
| **傷害意外保險型**| `injury` | 強調「外來、突發、非疾病」的意外傷害事故所導致的傷害、骨折、意外身故或意外住院等給付。 |
| **投資型保險型** | `investment`| 涉及金融市場、專設帳戶配置、資產評價等具備投資性質的理賠或給付項目。 |
| **壽險與年金保險型**| `life_annuity`| 圍繞生存與壽險返還、生存保險金、滿期保險金、定期生存年金、保證年金給付等項目。 |

> [!IMPORTANT]
> **資料 SSOT 原則**：在執行首次分類拆分時，我們**直接讀取並運用 `base_claim_items.json` 中現有的 40 多個既存項目內容**，僅對其進行險種標記與拆分，**不透過 LLM 重新生成或重寫表達式**，以確保既存精算邏輯、`logic_structure` 與 `parameters` 100% 完整保留。

## 3. 具體任務內容與環節

### 環節 A：首次自動分類拆分工具
* **目標**：開發 `src/classify_claim_items.py`。
* **內容**：
  * 讀取現有 `data/definitions/base_claim_items.json`。
  * 引入並套用 `src/classify_definitions.py` 中的關鍵字引擎與 LLM 語義分類器。
  * 保持既有理賠項目表達式（`logic_structure`、`parameters` 等）完全不變，將項目寫入對應的 5 個子 JSON 檔案中。
  * 確保拆分後的 5 個檔案總筆數與原檔案完全一致。

### 環節 B：升級管理工具 (`manager.py`)
* **目標**：提供理賠項目的精細管理與控制台審查。
* **內容**：
  * **合併載入**：在 `target_type == "claim_item"` 下，自動從 5 類子庫載入並合併資料，相容舊有 list 顯示。
  * **人機互動晉升 (`promote`)**：
    * 當有商品萃取出的 `NEW_GENERAL` 理賠項目要晉升時，控制台印出其**完整表達式細節**（包含 logic_structure 與 parameters），供人員審查。
    * 提供分類推薦（General / Health / Injury / Investment / Life_annuity）與互動選單。
    * 寫入選定子庫，並執行**跨庫去重**（自動從其餘 4 個子庫中剔除同 code 既存項目）。
    * 自動批次更新商品 JSON 的 status。
  * **重新分類 (`reclassify`)**：
    * 支援理賠項目的重新分類（跨子庫搬移）與刪除，並自動執行跨庫防禦性去重。

### 環節 C：升級 Pipeline 與對齊機制
* **目標**：在商品解析時實作雙層對齊。
* **內容**：
  * **險種動態載入**：Pipeline 依據商品险种（`detected_category`），動態載入「通用庫 + 商品險種庫」至 `context.base_claim_items`。其餘三個庫載入至 `context.fallback_claim_items` 作為備用。
  * **Fallback 對齊與融合**：在組裝 JSON 時，若 `benefit_code` 不在主要子庫，則循序比對備用庫。若在備用庫命中（代號/名稱/同義詞匹配），則將 classification 轉換為 `EXISTING_MATCH`，修正為標準 code，並與既存表達式融合，避免產生重複的 `NEW_GENERAL`。

## 5. 批量（160+ 商品）具體實作項目設計

為了應對真實環境下極大量 `NEW_GENERAL` 理賠給付的審查與一致性斷鍵痛點，本階段引入兩大核心自動化實作項目：

### A. 批次語義聚類與去重工具
我們將在 `scratch/` 開發大批量給付分析工具，其核心工作流如下：
1. **大批量提取**：一次性遍歷 160+ 商品的 JSON 解析結果，搜集所有標記為 `NEW_GENERAL` 的理賠給付對象。
2. **同義詞消歧與字面去重**：依據給付的 `display_name` 與 `synonym_map` 進行去重（如將「意外死亡給付」、「身故保險金」收攏為標準的 `DEATH_BENEFIT`）。
3. **大模型語義 Embedding 相似度聚類**：
   - 使用 Gemini 的 Embedding API，將數百個碎片化理賠給付的白話描述轉化為特徵向量。
   - 透過聚類演算法（如 K-Means 或層級聚類）將相似度大於 0.85 的理賠給付自動聚合至同一個「標準理賠給付群組」。
   - 生成批次晉升對照表，讓管理人員可以在控制台以「群組為單位」進行批次覆核與一鍵晉升（自動寫入子詞庫並聯動更新所有商品 JSON 的 classification），大幅節省人機互動審核時間。

### B. 參數來源自動診斷與標記引擎
為了讓每個理賠給付的參數（parameters）能精準與名詞定義、系統變數或使用者輸入對齊，我們實作參數來源三向診斷：

1. **名詞定義對齊型 (`DEFINITION_ALIGN`)**
   - **定義**：該參數的值與 Pipeline 第一階段解析出的「名詞定義」完全一致。
   - **診斷邏輯**：該 `param_name` 可能存在於 `base_definitions_*.json` 的 Code 列表中，或其中文名稱存在於名詞定義 display_name 中。
   - **實作規範**：如檢測到中文同義（如「保險金額」）但 Code 不一致（如 `INSURANCE_AMOUNT` v.s. `SUM_INSURED`），診斷引擎會自動阻斷並進行自動標準化重命名，防禦命名空間斷鍵。

2. **系統衍生與計算型 (`SYSTEM_DERIVED`)**
   - **定義**：該參數是由精算公式在執行時，系統自動計算出來的中間衍生變數。
   - **診斷邏輯**：其 `value_binding.binding_type` 為 `SYSTEM_CALCULATED` 且在 `logic_structure` 的 `python_logic_eval` 或是 `depends_on` 依賴中能找到與其關聯的計算公式（如 `DAYS_SINCE_ACCIDENT`）。

3. **外部輸入型 (`USER_INPUT`)**
   - **定義**：該參數代表網頁介面上需要由要保人或理賠人員手動填寫/勾選的變數。
   - **診斷邏輯**：既非名詞定義中的 Code，又無系統公式計算公式。
   - **實作規範**：將其 `value_binding.binding_type` 標準化為 `USER_INPUT`（如. `ACCIDENTAL_MEDICAL_DAILY_BENEFIT` 日額金額）。

藉由以上兩項大批量自動化工具，我們將大幅降低 160+ 個保險條款整理過程中的人力覆核成本，確保產出的精算模型 100% 精準與系統一致。
